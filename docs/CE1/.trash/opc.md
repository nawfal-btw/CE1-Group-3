# MVP Application Architecture

This is a greenfield design for the application only. The MVP is a Go modular monolith with one PostgreSQL/PostGIS database. It provides CRUD APIs and a small WebSocket channel for live updates.

```text
Client
  | HTTP / WebSocket
  v
Transport -> Application services -> Domain -> Repository (sqlc) -> PostgreSQL
```

Dependencies point to the right. HTTP, WebSocket, and SQL details never enter the domain package.

## Responsibilities

### `cmd/api`

`main.go` is composition only: read configuration, open the database connection, construct services, register routes, and start the server.

### `domain`

Contains the canonical business model and state-transition rules.

- `incident.go`: incident data and lifecycle, for example `open -> resolved -> closed`.
- `resource.go`: vehicle/resource data and lifecycle, for example `available -> assigned -> en_route -> on_scene -> available`.
- `assignment.go`: links a resource to an incident.
- `location.go`: validated latitude/longitude value used by incident and position data.

The domain decides whether a transition is legal. A client cannot directly set arbitrary status values through a generic CRUD update.

### `application`

Each file provides use cases for one capability. Services load data, call domain methods, save changes in a transaction, and notify WebSocket subscribers after successful persistence.

- `incidents.go`: create, retrieve, list, edit descriptive incident fields, resolve, close.
- `resources.go`: create, retrieve, list, edit resource details.
- `assignments.go`: assign and release resources.
- `positions.go`: store a resource position and publish its update.

This is also the authorization boundary: a service checks whether the current actor may perform its use case. The first MVP may use a simple dispatcher/responder role model.

### `repository/postgres`

Contains database-facing implementations. This is the only application package that imports `db/generated` from `sqlc`.

Repositories translate generated row types to application/domain types. They do not decide whether a resource may be assigned or whether an incident may be closed.

### `transport/http`

Handlers decode JSON, validate basic request shape, call an application service, and return JSON responses. They contain neither SQL nor domain rules.

Start with these endpoints:

```text
POST  /api/v1/incidents
GET   /api/v1/incidents
GET   /api/v1/incidents/{id}
PATCH /api/v1/incidents/{id}
POST  /api/v1/incidents/{id}/resolve

POST  /api/v1/resources
GET   /api/v1/resources
POST  /api/v1/incidents/{id}/assignments
POST  /api/v1/resources/{id}/positions
```

Use action endpoints for state changes, such as resolving an incident or assigning a resource. This makes valid operations explicit.

### `transport/websocket`

The WebSocket hub broadcasts committed changes, initially:

- `incident.updated`
- `resource.assigned`
- `resource.position.updated`

WebSocket is not authoritative. On connection or reconnection, a client first obtains current state through HTTP, then receives subsequent events.

## Database

PostgreSQL is the source of truth. Enable PostGIS in the first migration to store map locations as `geography(Point, 4326)`.

```text
incidents
  id, status, title, description, location, created_at, updated_at

resources
  id, call_sign, kind, status, created_at, updated_at

assignments
  id, incident_id, resource_id, status, assigned_at, released_at

resource_positions
  id, resource_id, position, observed_at, received_at
```

Relationships:

```text
incident 1 --- * assignments * --- 1 resource
resource 1 --- * resource_positions
```

Key decisions:

- Use UUID primary keys generated by PostgreSQL.
- Constrain status columns to known values; Go domain code owns transition rules.
- Add a unique partial index so a resource cannot have more than one active assignment.
- Add GiST indexes to incident and resource-position geography columns for map queries.
- Store both device-reported `observed_at` and server-received `received_at` for positions.

## Migrations and Queries

Schema changes live in `db/migrations/` and are run with `golang-migrate`.

```text
000001_initial_schema.up.sql
000001_initial_schema.down.sql
000002_add_positions.up.sql
000002_add_positions.down.sql
```

Migrations are immutable once shared. Any correction is a new migration.

Handwritten queries live in `db/queries/`; `sqlc` generates typed Go access code into `db/generated/`.

```text
incidents.sql:  CreateIncident, GetIncident, ListIncidents, UpdateIncidentDetails
resources.sql:  CreateResource, GetResource, ListResources, SetResourceStatus
assignments.sql: CreateAssignment, ReleaseAssignment, GetActiveAssignmentByResource
positions.sql:  CreateResourcePosition, GetLatestResourcePosition
```

Assigning a resource is one database transaction: verify availability, create the assignment, and update resource status together. This prevents concurrent dispatchers assigning the same resource twice.

## Later, Not MVP

- CAD integration: add an adapter package that calls application services; do not let external CAD models enter the domain.
- Fine-grained departmental roles and audit history.
- More detailed incident/resource state machines.
- External event delivery or durable outbox pattern.

## First Slice

Implement only incident creation and viewing first:

1. Create the initial `incidents` migration.
2. Add `CreateIncident`, `GetIncident`, and `ListIncidents` SQL queries and run `sqlc`.
3. Implement the incident domain model, service, repository, and HTTP handlers.
4. Test domain validation, repository queries against PostgreSQL, and HTTP responses.

Then add resources, assignments, and live positions as separate vertical slices.
